# Assessment Coverage Audit

## Purpose

This audit compares the current implementation with the application-security assessment specification adopted on 2026-09-01. It describes implemented behavior only; a documented category is not evidence that a target was tested for that category.

## Safety invariants

- Every network request is issued through `ScopedHttpClient`, which calls the scope engine before the initial request and before every redirect.
- Only bounded `GET`, `HEAD`, and `OPTIONS` requests are available to automated assessment modules.
- Redirect probes do not follow an out-of-scope destination.
- The engine does not automate credentials attacks, state-changing requests, destructive payloads, resource-exhaustion tests, command execution, data extraction, or malware.
- Indicators that cannot be safely confirmed are retained as observations or findings with `MANUAL_VERIFICATION_REQUIRED`.
- Findings require persisted evidence. Scanner output with no evidence is not normalized into a finding.

## Priority implementation order

1. **Completed P0 batch:** passive client analysis, state-changing form/CSRF indicators, inert query reflection, and non-followed open-redirect validation.
2. **P1 authenticated assessment contract:** encrypted operator-supplied test sessions, identity/role test matrix, session lifecycle, and access-control response comparison.
3. **P1 protocol and artifact depth:** constrained GraphQL query contract, JavaScript endpoint extraction, bounded artifact checks, and enhanced TLS posture.
4. **P1 intelligence:** confirmed/probable/unknown version labels plus an authoritative, timestamped advisory source.
5. **P2 engagement-specific modules:** controlled callback SSRF validation, business-logic workflow definitions, and conservative abuse-control observations.

## Longitudinal and reporting implementation

- Findings persist stable correlation lineage, recurrence count, monthly status, and remediation priority.
- `RESOLVED` is emitted only when the current profile, URL/endpoint/request coverage, and relevant deterministic modules are comparable. Otherwise a missing prior finding is `UNVERIFIED`.
- Executive, complete technical, PDF-ready, JSON, and per-finding reports are generated from persisted evidence.
- Dashboard summaries expose severity, `NEW`/`RECURRING`/`REGRESSED`/`RESOLVED`/`UNVERIFIED`, `FIX_NOW`/`FIX_NEXT`, measured coverage, and validated Qwen status.

## First implementation batch acceptance criteria

- New checks operate only on crawler evidence or scoped `GET` requests.
- Active probes honor the remaining scan request budget and configured rate.
- External redirect destinations are observed from `Location` and never requested.
- Potential secrets are classified and redacted; values are never persisted by the new scanner.
- Each normalized finding has evidence and conservative severity/confidence.
- The report states **NO FINDINGS OBSERVED** rather than claiming the target is proven secure.
- The complete report contains a ranked website weakness summary and remediation priorities.
